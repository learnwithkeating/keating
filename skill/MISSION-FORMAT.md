# MISSION.md Format

`MISSION.md` lives at `learners/<your-id>/MISSION.md` and captures the _reason_
the user is learning this topic. Every teaching decision traces back to it.

## Template

```md
# Mission: {Topic}

## Why
{1-3 sentences. The concrete real-world goal. What changes in their life or
work when they have this skill? Not "to understand X" - the outcome under it.}

## Success looks like
- {A specific, observable thing the user will be able to do}
- {Another specific thing}

## Horizon
{When must the user still know this? A date to work back from (2026-12-15), a
duration (18 months), or `indefinitely`. One line.}

## Constraints
- {Time, budget, prior commitments, learning preferences - anything that bounds
  the approach}

## Out of scope
- {Adjacent topics the user explicitly does not want to chase right now}
```

## Rules

- **One mission per workspace.** Two unrelated goals are two workspaces.
- **Concrete over abstract.** "Run a half marathon by October" beats "get
  fitter."
- **Push back on vagueness.** If the user cannot articulate why, interview them
  before writing anything.
- **The horizon is a retention question, not a deadline.** Ask "when must you
  still know this", not "when is the exam" - the second is what they will
  answer first, and the first is what sets review timing.
- **Leave the horizon out rather than guess it.** The scheduler reads it; an
  invented horizon moves every review the user gets. An absent Horizon means
  the platform keeps its default, which is the honest state until the user has
  answered.
- **Revise when reality shifts.** When the user's goal moves, update this file
  rather than leave a stale mission steering future sessions.
- **Keep it short.** A mission past a screen has become a plan, not a compass.
